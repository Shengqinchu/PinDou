# Studio 文案维护规范

店主要求（2026-09-08）：文案要落档和规范化、模块化，只有店主要求改的时候才改。

## 单一来源

- `05_studio/src/content/pages-*.json`：页面文字，固定键对应中/英两个值。
- `components-*.json`：菜单、共享组件、后台、辅助名称。
- `data-*.json`：相册说明、历史商品、错误字典和状态名称。
- `studio-profile.json`：公开地址、微信和电话；`experience-rates.json`：店主提供的展示价格。
- `journal-posts.json`：原帖/摘录，保留来源、完整性类型和原始正文。正文不由模型改写。平台话题/表情编码只在显示层解码。
- `approved.json`：明确授权后的内容哈希、SEO标题/介绍。它不是翻译来源，也不是日常开发应更新的版本文件。
- `STUDIO_COPY_BE46A3D.json`：改版前静态双语调用基线，不再编辑；完整旧源码仍可由 Git 的 be46a3d 恢复。
- `STUDIO_COPY_CATALOG.md`：当前内容的可读目录。

## 修改流程

1. 找到用户明确要改的句子/功能，记录原话、PDF页码或澄清事项，写入 STUDIO_COPY_CHANGES.md。
2. 只修改相应内容键和必要英文对应；键名保持不变。不能因为换字体、调整行宽或增加动效而换句子。
3. 需要换行时，优先使用布局；用户指定的换行存成内容中的 `\n`。不擅自替换标点、品牌名、单位或口吻。
4. 检查未授权内容与基线一致。更新获授权的批准哈希：`node scripts/content-catalog.mjs --approve --source=<具体用户要求/记录>`。普通构建禁止调用此模式。
5. `node scripts/content-catalog.mjs --render-catalog` 导出目录；`npm run check:copy` 验证；字体新增字符时重建子集。
6. Git diff 同时展示内容、授权记录与批准哈希。未经用户指示，不“顺手润色”或重译。

订单编号、顾客姓名、数据库价格、时间表、后台保存的营业时间与容量是动态数据。修改这些已授权经营设置不需要改宣传文案；前端只替换模板参数，不能拼接出不同含义的声明。

构建检查拒绝：内容模块哈希改变、新增/删除未批准模块、SEO文案改变、组件里重新出现中文硬编码或静态 tr 文案。检查不会自动批准任何变更。
