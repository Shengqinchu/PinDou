# PinDou 完整迁移执行与回退手册

**状态：2026-09-18 已完成。** 生产目标 `36.139.201.94`，到期 **2027-09-18**；当前配置见 [服务器资产](SERVER_ASSETS.md)，最终结果见 [迁移验收](PINDOU_FULL_MIGRATION_ACCEPTANCE_20260918.md)。下方保存原计划、冻结边界和回退步骤，不作为重新迁移或销毁旧机的指令。

原计划依据：[2026-09-18 现场调查](../01_research/PINDOU_FULL_MIGRATION_ASSESSMENT_20260918.md)。文中的“尚无”“尚未”按所处历史阶段理解，最终结果以验收为准。

## 1. 迁移完成的定义

1. 所有现存业务、数据库、文件、历史发布、备份、配置和系统存量资料都有可核对的去向；没有“为了小磁盘删历史”。
2. 正式域名仍为 `pindoupuppy.com`，网站/小程序所依赖的身份、预约、余额、商品、作品、内容、通知队列延续；同一时刻只有一个生产写入源。
3. 旧机上的全部持久文件完成保全：业务运行目录恢复到新机；完整旧系统资料另有安全归档。旧 machine-id、网卡、PID/socket、云初始化身份不会直接覆盖新机。
4. 新机恢复演练、业务验收、异机副本恢复和回滚过程有实测记录。仅网页可打开、SSH 能连接、复制命令成功都不等于完成。
5. 本次迁移不附带用户数据清理、账号重建、积分改规则、通知通道变更、数据库换型或新功能上线。历史已删除的原图不伪装成“已恢复”。

## 3. Phase A：目标、配置和备份准备

### A1. 购买和控制台证据

- 记录旧机到期、实例/磁盘/EIP/快照分别的计费和释放规则；目前安排基准为北京时间 9/25 22:41:52。
- 目标至少 80GB；核对实际可用空间/inode/IOPS，算上全历史、恢复工作目录和增长量。独立完整备份不堆在新机唯一根盘里。
- 核对活动价、续费价、地区、架构、带宽限速方向和流量计费。当前 495 元/年为 9/12 旧截图，不作为有效订单。
- 用候选机器实测网络。保持原访问架构，迁移当天不引入新代理。
- 决定整机保全形式：可用且已获费用授权的云快照/镜像，或者保留 Linux 元数据的持久文件归档；另保存应用一致性数据库副本。不能将仅同实例的快照视为已验证的异机恢复保障。

### A2. 配置与秘密清单

在受限目录加密保存，公开报告只记路径、权限、数量和校验，不写密钥值：

| 配置组 | 内容 |
|---|---|
| 应用 | `/opt/pindou/shared/.env`、`/opt/pindou/studio/shared/.env`、历史环境备份、shared 内 JSON 配置 |
| 身份 | JWT/管理员密码摘要、Studio auth bridge key、Authing、微信 AppID/secret、绑定身份、接收设置 |
| 通知 | serverchan-secret.json、customer-notification-templates.json、模板 ID、桥设备认证、DB 队列与租约 |
| 支付/邮件/AI | 原提供方配置、签名/回调校验、Resend 发信设置、现用 AI endpoint；迁移不消耗余额做无关试调用 |
| 入口 | 当前 Cloudflare ingress/DNS/TLS/Host/Access/缓存设置、正式 tunnel 凭据、Nginx 配置、证书/key |
| 系统 | systemd 与 drop-in、用户/组、sudo/SSH/known_hosts、cron/timers、日志配置、字体/共享库、包版本 |
| 本地维护 | 项目运维脚本、SSH alias/.env 中源目标记录、备份目标、Mac 两个短信桥的设备端 outbox/去重状态 |

当前数据后端是 local；即使 env 里还有 COS 配置，也不能在迁移时切换存储后端。保留正式 AppID 和域名，不以新建小程序/新账号代替搬迁。

### A3. 备份可恢复性

- 源机全树先做根目录/挂载清单。`/opt/pindou`、`/etc`、`/root`、`/home`、`/usr/local`、`/var`、`/tmp` 中持久普通文件和其他根级存量逐项归档，不只挑已知业务文件；归档目的地必须明确在扫描范围之外，防止把备份套回自己。
- `/proc`、`/sys`、`/dev`、运行中的 `/run`、socket/PID、交换区属于需重建的瞬时对象，记录处理规则；不是静默删除用户资料。旧启动/网络/云身份可入档，不覆盖新机当前身份。
- 保留 Linux 硬链接、软链接、权限、UID/GID、ACL/xattr 与时间信息。归档不在 Windows 上直接解包为唯一副本，避免丢失这些元数据。
- 对完整离线归档做 SHA-256，传到独立安全目的地后校验；实际抽取恢复两库、媒体、依赖包和一份历史 release，检查解密/解包/读取过程。完整文件比对安排在预同步阶段。
- 本次调查只有元数据和摘要，**不可以勾选“已有整机备份”**。

## 4. Phase B：预同步与隔离恢复

### B1. 先隔离，再放真实副本

1. 新机正式应用 unit、cron、桥接和生产 Tunnel 先保持停止；使用目标独立的系统身份及 root-only staging 目录。
2. 演练不得连接生产 Tunnel token。选择 SSH 端口转发、隔离临时 hostname 或独立测试 tunnel，限制访问。
3. 恢复到 disposable DB/media 副本。阻断通知/支付/AI等真实外呼，替换成测试 transport/接收人；仅“不开网页”无法阻止 startup worker 自动运行。
4. 原生成器过期原图清理在演练副本禁用；Studio 启动时会初始化表、对账、把 running 导入任务改为失败，所有演练操作都只能作用在副本。
5. 不开放真实 Mac 桥的消费入口。不要把真实库中的任务全改成 sent/skipped 来避免发送，这会破坏待迁移状态。

### B2. 完整复制和文件清单

- 先读取源 `current` 及 manifest，然后同步全部 release/shared/backups/static-history。在线 DB 文件及 sidecar 不作为最终一致性副本使用。
- Linux → Linux 采用可续传的 rsync；归档模式之外显式考虑 `-HAX --numeric-ids`。先 dry-run，对目标真实绝对路径做边界验证，不对源目录或未知目录运行删除参数。
- 两端本地生成结构化 manifest 后一次性传输比对：路径、类型、大小、SHA-256、软链接 target、权限/UID/GID、硬链接分组。不同机器 inode 数字不应要求相同，只比较组内链接关系。
- 源机约 66 万文件路径，硬链接很多：同 inode 只读一次内容；manifest/hash 尽量在服务器本地低优先级限并发完成，避免每个小文件跨境 SFTP stat。
- 不变 releases 提前全量验证；对仍可能增长的 shared/日志记录验证时间和差异。执行完预同步后，正式停写只处理最后变化。
- 带宽和小文件开销通过首次复制实测。8Mbps 理论约 1MB/s 只是速率换算，实际迁移可能受源出网、目标入网、跨区和磁盘限制；不能把目标广告带宽直接当迁移实际吞吐。

### B3. 运行时恢复

- 源旧 Python 二进制/依赖清单保全；新机同时验证生成器解释器、Studio 解释器、共享库、字体和 CA。pip freeze 不能替代系统依赖清单。
- 生成器 venv 链依赖六月 release 与绝对 uvicorn 入口。先保证路径链完整；如采用重新建 venv，必须在演练阶段处理并确认全部入口，不在最终切换临时修路径。
- 两个 wheel 已知存在：certifi-2026.7.22 与 curl_cffi-0.14.0。将它们纳入依赖归档；从 `/tmp` file URL 重建需要文件真实可用或预先改为已核验的包来源。
- 切换阶段使用已验证的同一代码/运行配置；不要重新打包当前脏工作区或临时拉 latest。

### B4. 演练验收

| 验证项 | 通过标准 |
|---|---|
| 两库结构和内容 | 全 17 + 67 张表（执行时重数）、schema/index/trigger、自增状态、逐表内容摘要匹配；完整性通过 |
| 跨库关系 | Studio owner_id / miniapp user_id 到 users.openid 关联缺失为 0；身份/角色保持 |
| 钱包/来源 | 余额和流水一致，管理员代建/补录不获自助积分；原有自助奖励和幂等边界不被修改 |
| 预约 | 在测试副本验证小时/包天、两小时最短、刚好两小时可约、短空档关闭、容量与重叠、取消/确认；日期以 Toronto 计算 |
| 商品/内容 | 全部商品与规格/库存/价格、已发布/草稿、相册/详情、当前和历史静态资源加载 |
| 账号 | 网站/小程序关联、管理员入口和权限、旧账号数据、上传和下载；无需重新注册 |
| 原有图纸服务 | 作品/图纸/预览/下载与原账号一致，保留页面隔离；不是将旧 AI 页面重新放回小程序 |

## 5. Phase C：最终冻结和切换

演练通过后才确定维护窗口和停写时间预算。若时长超预算或出现 hash/跨库不一致，在新机开放写入前恢复旧机，重新准备。

### C1. 关闭新业务写入，排空正在进行的操作

| 写入方 | 冻结动作及验证 |
|---|---|
| 网站/小程序顾客 | 入口维护模式，拒绝预约、订单、上传、登录状态变更等写入；提示稍后重试，不能把未保存的写入返回成功 |
| 店主后台/运维 | 暂停内容发布、预约管理、余额和商品修改、发布脚本；确保无另一任务同时部署 |
| 支付/第三方回调 | 核对提供方重试规则；维护期间可靠保存回调或返回其可重试失败，不能丢弃并伪回成功。不能确认重试保证时先解决回调承接再切换 |
| 两个应用 | 等待实际正在执行的生成/导入/请求结束，再停止原服务和附带 worker；有历史 pending 订单不等于必须删除 |
| Mac 短信桥 | 暂停领取，等在途发送回报入库或明确记录 unknown/租约；设备端持久 outbox 一并保留 |
| 清理/计划任务 | 暂停会写业务目录/DB 的 scheduler、cron/timer；保留原启用状态清单供新机受控恢复 |
| Cloudflare | 旧入口维护页继续可见；目标正式 connector 此时仍不启动 |

停完后用进程、连接/文件句柄和两次内容摘要验证没有隐藏写入者。不能只检查“HTTP POST 已禁用”，因为通知 worker、GET 触发诊断/统计、后台清理和外部设备也可能写。

### C2. 最终数据与清单

1. 在共同停写时点对两库产生一致副本，首选 SQLite backup API。主库/WAL/SHM 不能只拷一部分；不要在不确定 WAL 是否合并时手动删除 sidecar。
2. 同时冻结业务文件副本和所需配置；记录 UTC/北京/Toronto 时点、release、所有表行数/摘要、schema、文件清单、通知状态与租约。
3. 将最终副本安全传到目标 staging；核对 SHA-256、两库完整性、全部逐表摘要、跨库 ID 和余额，再安装到目标正式路径，检查权限与绝对路径。
4. 对预验证静态树确认没有变化，对动态差异做哈希核验。只匹配总字节数或文件数量不足以放行。
5. 最终冻结副本也进入独立备份目的地；记录哈希和恢复方法。既有 1,391 本地授权数/队列状态按当时值迁移，不使用本报告值回写。

### C3. 只开启一个生产写入源

1. 旧服务和全部消费者保持停止；停止旧正式 cloudflared connector，验证断开。不得让它靠自动重启再次连上。
2. 目标只做不会启动业务 worker 的离线检查；正式启动新应用前重新核对真实 env、DB/media 路径、模板、发送开关和租约。**新服务启动即视为可能写入的分界点**，不能等第一个顾客访问才算。
3. 启动新两服务与 Nginx，再启动唯一的正式 connector。恢复新机所需任务，避免临时测试入口仍可绕过维护隔离访问真实库。
4. 验证公网请求确实到目标：目标访问日志与请求标记对应，旧业务进程停止；静态 HTML build 相同不证明已经换机。
5. 在限定的测试身份下进行事先确定的验收写入，确认记录仅出现在新库；不改真实客户积分，不自动创建收费订单或发给真实顾客。测试通知只能发给明确指定并同意的接收人。
6. 新平台/设备检查通过后恢复 Mac 桥和正常入口。旧机不再自动恢复业务 unit，保留为只读回退资料。

Cloudflare 同 Tunnel replica 都可能接到请求，测试不能使用生产 token。[官方说明](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-availability/)

## 6. 回退

| 时点 | 正确操作 |
|---|---|
| 新机还没有任何写入（包括 startup worker） | 停目标入口/应用/任务，确认完全退出；旧冻结库/文件仍未被覆盖时，重新开旧机服务与唯一 connector，再恢复入口 |
| 新机已开始写入 | 重新进入维护，冻结新机和外部桥，保存新两库/文件/通知结果/回调，在旧机恢复**新状态**并验证后再切回；不能直接启用旧快照 |
| 旧机已不可用/到期 | 使用独立异机备份恢复到可用目标；此时没有“切回旧 IP”的回退选项 |

回退涉及真实通知已发送、支付已完成、积分/预约已变化时，以最新业务结果与幂等记录为准。重复发通知、重复奖励或漏掉新预约都不算成功回退。迁移当天不做删旧机、取消订阅、销毁密钥或清理历史文件。

## 7. 上线后验收和交接

- 外部平台：微信请求/上传/下载合法域名与新来源 IP 白名单，Authing 回调，支付签名/回调，邮件、AI、COS 配置用途；正式域名保持不代表 IP 白名单无需核对。
- 客户端：网站桌面/手机与微信真机，首页、预约、账号、店主后台、商品图片和旧页面静态资源；原有二维码/收藏入口继续指向正式域名。
- 数据：所有正式记录与最终冻结基线对得上，切换后的新增可逐项解释；预约来源保护、钱包、订单、作品、内容历史、通知租约/未知结果保持。
- 运行：重启/崩溃、延迟、错误、资源、磁盘/inode、通知任务积压与设备心跳；值保持不变不发送无意义提醒。
- 备份：在新机上线前落实恢复过的异机备份；后续建议两库和动态资料做定期一致副本、按变化同步媒体，历史完整归档长期保留。具体频次/RPO/保留份数按业务要求落定，不能擅自清除历史。
- 回退期限：写明旧机可用到的确切时间；争取 9/22–23 切换，若必须 7 天则单独解决续期，不把旧机即将到期当成灾备已完成。
- 更新运维：项目部署目标、SSH 主机校验、本地私密 env/alias、备份入口和操作文档，防止以后发布又打到旧 IP。
- 报告：准确写明已验收和未测试部分；真实通知的接口成功与设备实收分开记，未做真实支付不写“支付全链通过”。
