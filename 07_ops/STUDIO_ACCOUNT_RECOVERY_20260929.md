# 小程序邮箱登录与微信重复账号修复

## 问题与规则

2026-09-29 店主授权修复顾客原邮箱账号与空白微信账号分离的问题，并排查同类用户。原邮箱账号仍存在，资产没有丢失；原登录页在邮箱密码验证成功后强制绑定微信，绑定返回 409 时没有保存邮箱登录结果。后台填写的微信联系号不等于 OAuth / 小程序登录绑定。

- 邮箱密码登录独立成立。新版“同时绑定当前微信”为可选项；微信不可用或绑定冲突都不撤销已验证的邮箱登录。
- `/native/bind` 对有效双重身份的绑定冲突返回 `200 {linked:false, reason:wechat_binding_conflict}`，保留现有绑定。线上旧版在收到成功状态后也能保存原邮箱会话；新版明确解释未绑定。非法登录或微信凭据仍拒绝。
- 微信入口增加“已有邮箱账号，去登录”，未绑定时说明直接继续会创建独立账号。已绑定的微信仍不能再次注册另一邮箱账号。
- 注册时间用于选择已经确认同一人的保留账号，不能作为归属证明。手机号、微信联系号、昵称相同不能自动合并。

## 针对已确认空白重复号的恢复

`studio_account_recovery.py` 默认只读预检，需要明确的来源、目标顾客编号。执行必须满足近期已验证双方身份的冲突记录，或店主明确核实并授权这一对账号；不会批量自动运行。

```text
python3 studio_account_recovery.py --list-conflicts
python3 studio_account_recovery.py --source PD-NEW --target PD-ORIGINAL
python3 studio_account_recovery.py --source PD-NEW --target PD-ORIGINAL --owner-confirmed --apply
```

该工具仅在当前生产主机执行，申请写入前备份两个 SQLite 库。短事务内重新检查账号、绑定、余额和业务引用：来源必须是当前小程序生成的空白账号，没有邮箱密码、自定义资料、预约、订单、作品、任务、会员权益或已消费积分；只允许未使用的初始赠送。目标必须是仍有效的原邮箱密码账号，且没有另一条小程序绑定。

实际修改仅包括微信入口归属、来源账号的 Studio 停用/归档标记、冲突状态及追加审计。原账号编号、密码、余额、积分、作品、订单、预约和历史账本均保留，不叠加两份注册赠送。生成器库不写入。旧空号 JWT 在 Studio 返回 401，重新登录后走修正后的微信绑定；不会把旧 JWT 自动兑换成原账号资产访问权。此处停用范围是 Studio，不声称撤销生成器服务所有旧 JWT。

每次执行以完整表内容指纹校验只变更许可的五张表，两个库完整性检查通过才提交。重复运行只报告已修复，并核对当前微信身份与原审计相符。备份/回执存于服务器私有 `studio/backups/account-recovery-*/`，顾客记录不提交 Git。

## 其他可能受影响的用户

检查时有 26 个顾客记录、12 条原生小程序绑定、5 条 Authing 绑定，未发现重复原生身份或悬空关联。保留期间的四次原生绑定 409 与本次报告一致；不能据此排除更早或尚未再次登录的用户。资料空白的账号不等同于受影响账号。

1. 先让正确的邮箱账号可登录，不要求顾客再注册、清空资产或修改密码。
2. 新发生的绑定冲突只在邮箱会话和微信凭据均有效时记入受限数据库；运维按 `--list-conflicts` 查看编号配对和时间。日志不记录密码、JWT 或原始 OpenID。
3. 经核实同属一人且新号空白，使用默认预检，再执行绑定恢复并复核资产。
4. 两边都有资产、多个第三方绑定、已消费赠送、会员或身份不确定的情况，工具拒绝修改，保留两边数据，单独制定迁移清单；不可直接删号或按最早注册时间批量归并。
5. 本次没有向顾客批量发送通知。确认登录恢复可以由店主让顾客重新打开小程序，若仍显示空号，退出后点微信登录，或直接用原邮箱登录。

## 回退注意

部署前保留上一个应用 current 与两个数据库快照。仅部署失败时由既有部署器恢复应用；账号修复是独立、可审计的事务。已经成功恢复账号后，不可恢复整个旧库覆盖新预约；如确需撤销，先只读核对后续业务，再单独撤销指定绑定及停用标记，并追加审计事件，不能删除审计或抹掉账本。向前修复优先于回退到仍有登录缺陷的版本。
