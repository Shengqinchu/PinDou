# 移动云上海：PinDou 实际工作负载与配置估算

日期：2026-09-12。范围：现有网站、预约/店主后台、商品目录、图纸本地计算及图片处理。用户要求“能不能算出来或者测试出来，移动云上海我们需要多少配置”。

后续收到具体套餐截图：4核8GB加到8M约440元/年，而8核16GB、80GB、8M为495元/年；针对该报价组合优先后者，详见[套餐与代理方案](PINDOU_SHANGHAI_PLAN_AND_PROXY_20260912.md)。下文保留按容量需求得出的分档，性能需求与套餐性价比分别判断。

## 选型结论

**当前轻量经营可从 2 vCPU / 4GB 开始；购买长期使用的上海实例，建议 4 vCPU / 8GB、80GB SSD。现阶段没有测出必须使用 8 vCPU / 16GB 的需求。** 这是按现有 CPU 等级、当前业务和本轮受控工作负载给出的建议，不是对所有未来并发的保证。

| 配置 | 建议用途 | 限制 |
|---|---|---|
| 2 vCPU / 4GB | 省预算起步；日常浏览、预约、管理，少量图纸生成 | 多张图纸一起生成会等待；图片上传、生成和后台大图处理不宜无限并发 |
| 4 vCPU / 8GB | 小店长期使用的推荐档；为上述任务重叠、更新部署和增长留余量 | 目前单进程的计算与序列化路径不会随核心数线性提速，仍需程序并发优化 |
| 8 vCPU / 16GB | 促销价格接近推荐档，或后续还要合并其他服务时的余量档 | 本轮未证明是刚需；不能期待仅换配置就消除排队或加拿大至上海的网络延迟 |

磁盘建议保留 **80GB SSD**，目前整机根盘已用约 32GiB。公网带宽可按 **10Mbps 起步、优先 20Mbps** 选；这是按图片与 API 数据传输量的规划值，本轮没有对云账户的带宽限速或加拿大运营商线路进行专项压测，也没有核对新套餐价格、续费或 SLA。

## 测试方法与边界

- 在现有上海服务器上运行独立临时服务，使用线上实际部署的代码，未使用工作区中尚未上线的生成器修改。
- 原机：8 个逻辑 CPU，Intel Xeon Processor，x86_64；15796MiB RAM；Ubuntu 22.04.5；根盘 79GiB。新实例即使也叫“4核”，若 CPU 型号、共享份额、磁盘或宿主机负载不同，仍需用本脚本复测。
- 通过 systemd `CPUQuota=200%/400%`、实际进程 `CPUAffinity=0,1 / 0,1,2,3` 限核，并记录 `cpu.max`。测试组内存上限 4GiB、禁止 swap、最多128个任务、最长240秒；进程降低优先级。**没有把整台生产机降到 4GB**；系统及已有业务的内存另行估算。
- 临时服务启用独立网络命名空间，无法连接外网；生产数据目录不可访问，系统文件只读，只有任务临时目录可写。未发送通知、未调用付费 AI、未创建真实预约或修改价格。
- 图像完全由确定性测试脚本合成：1024×1024简笔图、1280×960复杂渐变/噪声图，以及放大到1200万、2500万和6000万像素的 JPEG。并非读取顾客上传图片，结果不代表所有真实图片的最坏情况。
- 普通生成测试包含实际 `PatternBuilder.build`、网格预览、`to_labeled_grid_png`、前端 JSON 序列化。未计入真实用户鉴权、上传网络、数据库落盘、CDN与外部AI模型耗时。AI测试仅测试已取得预览图之后的本地处理部分。
- 三任务图纸测试用同进程线程并行，以观察与现有 AI 后台线程相近的计算争用。普通 `/generate/script` 的真实 HTTP 入口还有同步计算造成事件循环等待的问题，所以不能把这一组计算函数测试当作完整的普通生成 HTTP 并发验收。
- 查询使用线上已部署的预约和商品 GET 处理器，以及独立 SQLite 数据库：10000条合成预约（其中112条是未来14天确认预约）、232个商品。仅注册所测 GET 路由，无生产应用后台工作线程；未计入管理员鉴权和全部生产中间件。临时服务器与负载客户端共享本次 CPU 限额，因此吞吐量包含客户端开销。
- 所有正式用例均完成，未发生 OOM、swap、计算异常或所测 HTTP 错误。共有14个正式资源配置/工作负载用例，HTTP计时请求共942次。短时结果用于容量决策，未做长时间稳定性或全站业务混合峰值验收。

## 图纸生成与图片处理实测

下表时间为首次运行之后的热启动值；3张表示同时开始的整批完成时间。每组通常2次运行，单张52/104组3次。小样本不报告虚假的统计置信度。内存为该测试 Python 进程全组历史峰值 RSS，**不是每张的内存，也不是整机内存**。

| 工作负载 | 限制核数 | 同时任务数 | 热启动耗时 | 进程峰值 RSS |
|---|---:|---:|---:|---:|
| 复杂图 → 52×52普通图纸 | 2 | 1 | 5.2–5.7秒 | 164MiB |
| 复杂图 → 104×104普通图纸 | 2 | 1 | 6.7–6.9秒 | 192MiB |
| 复杂图 → 200×200普通图纸 | 2 | 1 | 24.6秒 | 341MiB |
| 复杂图 → 104×104普通图纸 | 2 | 3 | 23.4秒/批 | 273MiB |
| 相同104×104负载 | 4 | 3 | 22.5秒/批 | 346MiB |
| 复杂图 → 200×200普通图纸 | 4 | 3 | 76.4秒/批 | 710MiB |
| 预览图 → 104×104 AI后处理 | 2 | 3 | 10.6秒/批 | 287MiB |
| 2500万像素照片规范化为PNG | 2 | 3 | 28.3秒/批 | 761MiB |
| 后台6000万像素照片缩至2400px WebP | 2 | 2 | 2.2秒/批 | 966MiB |

首次运行可能更慢，例如104×104复杂图首次约8.7秒，热启动约6.8秒。52×52带色号导出的时间也不保证比104×104更低，程序在不同网格尺寸采用不同标注策略；不要只按格子数推算总耗时。

主图纸测试的峰值内存没有接近4GB，明显问题是大尺寸与多任务等待。2核变4核，三张104×104同进程线程测试只从23.4秒改善到22.5秒；批次累计CPU时间约27秒，实际约只消耗1.2个核心。该结果支持“当前计算路径限制了多核收益”，不能归因于内存不够，也不能推断换8核会快一倍。

为区分代码并发方式与硬件，还在临时环境做了额外对照：相同6张104×104图纸，3个独立Python进程各顺序处理2张，2核下总计27.3秒、4核下19.9秒；同进程线程分两批则分别约48.2秒、47.6秒。独立进程对照包括子进程启动/导入开销，调度批次边界也不同，**只能用于证明优化并发有潜力，不能当作已上线后的端到端性能承诺**。峰值测试组内存约378/398MiB。生产并发架构没有修改。

## 预约和后台查询实测

请求包括商品目录、预约日历、后台预约列表和后台时段表。P95指95%的所测请求在该时间内完成；下表均为服务器内网测试，不包含顾客至上海的网络等待。

| 场景 | 限制核数 | 计时请求数 | P95 | 错误 |
|---|---:|---:|---:|---:|
| 单客户端持续查询 | 2 | 131 | 166毫秒 | 0 |
| 10客户端无间隔持续施压 | 2 | 123 | 1878毫秒 | 0 |
| 30客户端无间隔持续施压 | 2 | 159 | 3858毫秒 | 0 |
| 单客户端持续查询 | 4 | 133 | 164毫秒 | 0 |
| 10客户端无间隔持续施压 | 4 | 121 | 1508毫秒 | 0 |
| 30客户端无间隔持续施压 | 4 | 155 | 3534毫秒 | 0 |
| 30客户端，每个每5秒请求一次，均匀错开 | 2 | 120 | 165毫秒 | 0 |

最后一组在20秒发送窗口内计划并完成120次请求，约6次/秒。原始客户端 `duration_s` 还包含最后一次发送后等待定时器退出的空闲时间，不能拿其中约4.86 RPS误读成服务饱和吞吐量。最大响应约172毫秒，测试组（临时服务、负载客户端和监测脚本）峰值约88MiB。

“30个客户端每5秒请求一次”仅描述这组查询场景，**不等于保证30人同时生成图纸**。无间隔持续施压达到约9–11请求/秒时，现有单进程服务已经明显排队；4核下改善有限。数据库查询、返回值序列化与进程并发应继续优化，不能把“没有报错”写成“高并发体验良好”。

生产日志汇总最近约24小时共89782次请求，单分钟峰值325次，即该分钟均值约5.4次/秒；其中大量是后台/短信桥轮询以及本次测试前已有的运维操作，不是89782个客户，也不是每秒5.4次预约提交。本轮压力请求走独立端口，没有混入生产Nginx日志。所选查询用例与生产轮询的成本不同，不直接拿两者RPS相除宣称容量倍数。

## 内存、CPU、磁盘和带宽怎么算

1. **基础内存**：测前整机 `MemTotal - MemAvailable` 约921MiB，测后约936MiB，即约0.9GiB，包含系统与已有应用。它是当前观测，不是历史峰值。
2. **轻量使用**：基础0.9GiB加一个重图纸/图片处理组约0.3–1.0GiB，再留系统缓存和余量，4GB具有可用空间；不建议为了省一点预算降至1–2GB。
3. **任务重叠的保守预算**：基础0.9GiB + 三张大图纸0.69GiB + 三张大照片转换0.74GiB + 两张后台大图0.94GiB + 查询测试组0.12GiB，合计约3.4GiB，增加30%余量约4.4GiB。因此8GB是余量建议。**这是将分组峰值相加的估算，未实测所有这些任务同时发生，而且含部分共享库/基础进程的重复计算，偏保守。**
4. **CPU**：104×104复杂图单任务热启动约6.8 CPU秒；例如每分钟6张平均消耗约0.68核，尚须加上查询、上传、导出等成本。瞬间扎堆的体验由任务队列和并发方式决定，不能按平均CPU直接保证等待时间。4核为独立工作进程与后台保留空间；当前实现尚未完全利用它。
5. **磁盘**：当前79GiB根盘已用32GiB。原生成器历史发布目录约16229MiB、Studio发布目录2292MiB；业务共享目录分别154MiB和17MiB。增长不仅来自顾客图纸，也来自每次保留的部署版本。80GB当前更合适；40GB直接照搬当前磁盘内容余量偏小。未删除任何生产历史发布或修改保留策略。
6. **带宽**：20Mbps理论上约2.5MB/秒，10Mbps约1.25MB/秒，不含协议、拥塞和跨境延迟。104×104样例JSON约1.90MB，200×200约7.09MB；实际有压缩/缓存时传输更小，上传或外部AI图片传输也可能更大。测试中的2500万像素JPEG规范化后为约30.95MiB PNG，说明大图上传处理和发给外部AI的数据体积需要单独优化，不能只看原文件的5MB。本轮未测外部AI网络性能。
