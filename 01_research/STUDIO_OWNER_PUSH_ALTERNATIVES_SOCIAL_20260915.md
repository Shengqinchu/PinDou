# 店主持续通知：社区案例与官方能力复核

核查时间：2026-09-15，加东时间。范围：让店主持续收到预约提醒，尽量在普通微信内接收，避免逐条补小程序订阅授权。

后续执行：用户曾授权创建个人团队，同名团队和自建应用已创建；随后明确停止企业微信接入。本地草稿归档、未部署。最终澄清只要现有小程序自己的通知，误调方糖上限已恢复为原来的 5。用户真实授权后，自有小程序测试通过并确认手机收到，后续补充的 2 次授权留给真实预约。详见 [恢复实测](../07_ops/STUDIO_OWNER_ALERT_RECOVERY_20260915.md)。以下排序是历史研究判断，不是当前实施计划。

## 结论

有值得优先验证的替代路线：**独立建立企业微信个人团队 → 自建“小狗拼豆铺”应用 → 我们的服务器调用企业微信接口 → 店主通过微信插件在普通微信内接收。**

这与现有个人主体小程序是两套账号能力；不能因为小程序暂不满足“用工关系消息”的条件，就推断所有微信内持续推送都必须先迁移小程序主体。前面的方案比较范围不够完整，应把这条路线列为优先试验对象。

本次已确认官网有“个人组建团队”入口，官方帮助明确支持微信插件接收企业应用通知。**尚未创建我们的企业微信团队，也未验证新团队的实际应用权限、名称显示、费用提示和手机收件。** 因此结论是“有官方通道支撑、值得实测”，不是“已开通、保证永久免费无限发送”。

## 方案比较

| 方案 | 店主在哪里收 | 是否逐条补小程序授权 | 接入与费用判断 | 本店优先级 |
| --- | --- | --- | --- | --- |
| 企业微信个人团队＋自建应用＋微信插件 | 普通微信的企业入口及应用消息 | 不使用普通小程序的一次性授权计数；仍需成员加入、关注及通知开关有效 | 可由现有服务器直连，不需要购买方糖会员；社区报告个人可免费使用，账户级条件仍需实测 | 第一优先验证 |
| 网站 Web Push / PWA | iPhone 锁屏、通知中心及配对 Apple Watch | 正常使用时首次允许通知，之后不逐条授权；用户可撤回、清理数据可能需重新订阅 | 我们网站自建推送；苹果不要求加入付费开发者计划 | 很适合第二通道 |
| 公众号接口测试号 | 普通微信中的测试号消息 | 是另一套接口，不是小程序逐条授权 | 官方测试入口仍可访问；账户模板额度与实际收件未测 | 技术试验，不建议先把唯一营业提醒依赖放在测试号上 |
| 小程序用工关系消息 | 微信“小程序助手” | 专门的员工绑定和消息授权机制 | 官方要求非个人主体及支持的类目；与目前个人小程序条件不符 | 若以后主体和资质合适再评估 |
| 普通小程序订阅消息 | 小程序服务通知 | 仍受有效授权次数限制 | 可改善明确的授权入口，但不能把“保持选择”当作无限发送 | 保留给对应顾客流程及辅助通知 |

“首选”是根据本店偏好作出的工程判断，不代表上述任一通道有绝对送达保证。

## 企业微信路线：证据与接入边界

### 已经核实

1. [企业微信官方注册页](https://work.weixin.qq.com/wework_admin/register_wx)确实显示“没有企业？个人组建团队”。点击这个入口后显示微信扫码建团队；没有继续注册。
2. [官方微信插件帮助](https://open.work.weixin.qq.com/help2/pc/14797)说明：注册后开通对应微信插件，成员关注后可在微信接收企业应用通知。邀请二维码的 7 天有效期针对邀请链接，不是“每 7 天消耗完订阅次数”。
3. [官方发送应用消息接口](https://developer.work.weixin.qq.com/document/path/90236)允许应用主动向成员发送消息，并明确描述微信端接收行为。它与现有小程序的 requestSubscribeMessage 是不同通道。
4. [2026 年作者部署案例](https://linux.do/t/topic/1445185)给出这条路径及代码；[后续版本说明](https://linux.do/t/topic/1519190)还记录过非文本消息打包故障，说明有实现可参考，也不能不测试便直接照搬。

### 实施时检查

- 在应用可见范围中加入店主的企业成员账号；顾客不会因此自动成为成员，也不会自动获得这条通知。
- 使用我们自己的应用名称、图标和密钥。普通微信内会有企业/应用入口，不能承诺外观与当前小程序通知卡片完全一致。
- 配置服务器真实出口 IP，以及后台要求的可信域名或消息服务器验证；密钥留在自己的服务器。
- 按官方帮助开启“接收应用消息”，不要停用应用；关闭“仅在企业微信中接收消息”等会阻止同步的设置。
- 如果启用“在微工作台中始终进入主页”，官方接口文档提示微信端消息内容会受限；应按实际提醒展示需求配置。
- 官方接口有频率上限和接收范围限制，因此不采用论坛“无限制”的宣传。API 返回接受，也不等于手机已经展示或店主已经看到。

### 是否一定要安装开源推送平台

不一定。现有后端已经有店主通知队列、重试与发送状态，可以增加企业微信发送适配，而不是为了一个接口引入整套后台。可参考 [qingzhou-dev/push-server](https://github.com/qingzhou-dev/push-server) 的接口封装思路；其仓库声明 AGPL-3.0，复制或修改其代码需按许可证处理。直接依据官方 API 独立实现适配通常更贴合现有项目。

其他可比作者实例：[wangwangit/qywx-push 对应教程](https://linux.do/t/topic/770848?tl=zh_CN)、[Futaoj/lark_wechat_sync](https://github.com/Futaoj/lark_wechat_sync)。它们的 README 说明个人团队配置，但不能替代我们账号权限验证。

## 网站直接通知 iPhone

[WebKit 官方说明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)确认：从 iOS/iPadOS 16.4 起，添加到主屏幕的网页应用可以在用户点击后请求通知权限，获准后通知可以出现在锁屏和通知中心；不要求 Apple Developer Program 会员。

对于本店，可以把店主工作台做成主屏幕应用，使用“小狗拼豆铺”的名称和图标。初次需要店主添加到主屏幕并允许通知，之后按正常权限状态持续推送。这不是微信消息，若“必须微信内收到”是硬要求，只适合作为第二通道。

还需在实际 iPhone 验证：锁屏、关闭网页、切换网络、专注模式，以及清理网站数据后订阅失效的恢复。该方案的手机实测本次没有执行。

## 知乎/论坛里的其他建议如何取舍

- **把订阅申请放在店主日常操作后面**：[知乎文章《微信小程序订阅消息问题》](https://www.zhihu.com/tardis/zm/art/677125828)的搜索索引提到这一思路，正文直接访问被验证页阻挡。它仍依赖用户实际操作，不适合解决店主长时间不打开小程序时的持续提醒；不会实现文章提到的隐藏按钮之类交互。
- **公众号测试号**：[知乎的 GitHub Actions 推送教程](https://www.zhihu.com/tardis/bd/art/576446452)全文可读，[官方测试号入口](https://mp.weixin.qq.com/debug/cgi-bin/sandbox?t=sandbox/login)本次也能打开。但官方定位是接口体验和测试；本次未测它的当前额度和手机展示，因此只列为备选实验。
- **企业微信群机器人**：不要与自建应用的微信插件混为一谈；群、群成员关系和应用接收范围不同。不能只看到“企业微信机器人”就宣称能发到任意普通微信群。
- **统一推送平台、免费转发 SaaS**：它们封装下游通道，不能凭空解除微信平台限制。已经具备服务器时，优先评估直接接入官方接口，避免再把连续通知依赖在另一个免费平台额度上。
- **V2EX 的一次性订阅实践**：[2024 年订阅讨论](https://www.v2ex.com/t/1017858)、[近期提醒工具作者说明](https://www.v2ex.com/t/1241473)仍反映授权次数问题；这些不是“永久授权”依据。

## 建议的下一步与验收

优先验证企业微信个人团队：一次建团队和关注 → 创建本店应用 → 核对账号真实权限及是否出现费用要求 → 配置自己的服务器 → 经授权向店主本人发送少量测试通知。

通过后再接入现有预约队列。重点验收：多条预约逐条处理、重复任务不会重复通知、平台限流/断网后保留并重试、已处理预约不重放成新预约、手机锁屏和隔夜仍能收到、后台展示失败与积压。需要区分“已入队”“平台接受”“终端收件”“店主处理”，不能统称“已送达”。

网站 Web Push 可以作为后续补充，短信仍可承担独立备用提醒。核心目标是失败可见、任务可恢复和有备用通道，而不是声称单条微信接口绝不会漏。
