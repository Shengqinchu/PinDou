# 小程序与店主后台流畅度排查

核查：2026-09-15 加东晚间。来源：店主反馈“小程序和管理员后台厚重、卡，不如网页”，要求调查原因和可用优化方法。本轮为研究、只读线上测量与隔离实验；没有发布性能改造，也没有购买服务。

## 结论

可以优化。目前已证实小程序切页会重复创建页面、首次页面生命周期包含重复同步设备调用；网络往返也比服务器处理耗时大得多。当前证据不支持先升级服务器。滚动掉帧的具体占比仍须在店主实际手机、关闭调试的正式版上测量，不能把源码问题或桌面模拟器结果当成手机 FPS。

网页与小程序是两个实现：网页为 `05_studio` 的 Vue 页面；小程序为 `05_frontend` 的 uni-app / Vue 3 编译包，使用微信页面、组件和逻辑/渲染通信。网页图片优化不会自动改变小程序的切页与滚动实现。

## 适合本项目的处理顺序

1. **先改善管理端常用切换。** 工作台/预约/消息/账务采用同一工作区内首次访问再创建、随后复用的视图；详情仍用正常页面栈。保留搜索、分页、滚动位置，隐藏视图停止轮询。顾客主要入口的 tabBar 改造要同时审查现有生成器 tab 路由，不能只替换一个 API 就上线。
2. **减少同步工作和渲染通信。** 一次读取窗口信息复用尺寸/安全区，只有变化时再更新；滚动位置记录降低跨层频率。先保留表单、软键盘、安全区、旋转和返回位置行为，再做浏览器/原生回归。
3. **首屏内容尽早可用。** 已有会话快照先展示，后台更新只改实际变化的部分；账号资料、钱包、提醒绑定独立完成显示，避免非关键请求拖住整页。保留手动刷新、写后失效、账号隔离和权限撤销检查，不靠拉长所有缓存掩盖延迟。
4. **减少反复入场。** 顾客关键功能页不因每次切换重复播放长入场；保留品牌首页表现，普通操作反馈更短、更直接。保存动作马上执行，动画不成为等待条件；尊重减少动态偏好。
5. **后续再评估冷启动和大列表。** 测量首包解析/组件注入后再开按需加载、拆包；列表变长后再做虚拟列表。当前预约列表已有分页，不能因为“听说虚拟列表快”就先增加复杂组件。

本轮尚未实施上述性能改造。建议先完成 1–4 的一版候选，再以同机、同网、关闭调试的基线/候选比较首开、热切页、连续滑动和保存反馈；持续滚动记录长帧、点击记录到首个有效反馈及内容就绪的两个耗时。页面有缓存与无缓存分开统计，不预先承诺提升百分比。

## 官方与 GitHub 方案核对

| 来源 | 本次采纳或排除的原因 |
|---|---|
| [uni-app 性能优化专题](https://uniapp.dcloud.net.cn/tutorial/performance.html) | 官方解释逻辑层/视图层通信代价，建议减少 scroll 监听、过多节点和一次更新的数据量。与本地代码检查吻合。App-nvue、uni-app x 的建议不直接套到当前 Vue 3 微信包。 |
| [uni-app 路由 API](https://uniapp.dcloud.io/api/router.html) | 区分普通页面入栈、返回与 tabBar 切换。App 专属 animationDuration 参数不能用来宣称微信切页提速。 |
| [微信官方 WeUI 组件库](https://github.com/wechat-miniprogram/weui-miniprogram) | 可参考微信内的轻量列表/表单与交互方式，保持小狗品牌；它是 UI 组件库，不会自动修好请求和页面生命周期。 |
| [微信官方 recycle-view](https://github.com/wechat-miniprogram/recycle-view) | 用于只渲染可视范围的长列表。有固定项目尺寸及组件集成要求；当前短列表/已分页后台不优先引入。 |
| [uni-app 框架仓库](https://github.com/dcloudio/uni-app) | 当前继续使用 Vue 3，不将 App-nvue 或 uni-app x 的性能结论视为现有微信包的测试结果。 |

微信开发者文档直连在本轮检索工具中不可读，因此未把未读到的 Skyline 文档作为迁移结论。本次不建议先购买加速 SaaS：已定位的重复切页/调用需要改本地界面与生命周期代码，现有证据没有指向新增付费订阅的必要性。
